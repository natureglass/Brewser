# Brewser Forwarder Contract (v1)

Authoritative contract for Brewser **app forwarders** — the per-app `.nro`
launchers ("shortcuts") that appear in hbmenu and chainload Brewser to run one
app. This document is the compatibility guarantee: **old forwarders in the wild
must keep working across every future Brewser runtime update.**

Terminology (user-facing copy says "shortcut", never "forwarder"/"NRO"):
- **Forwarder** — the generated `.nro` in `sdmc:/switch/`.
- **Stub** — the generic launcher code embedded in every forwarder
  (`brewser-forwarder-stub`, `romfs:/forwarder-stub.nro` inside `brewser.nro`).
- **Bundle / embed** — an optional in-forwarder snapshot of the app's files.
- **Lite forwarder** — a forwarder with no bundle (link only).

---

## 1. argv contract (v1) — the durable cross-version guarantee

The stub chainloads Brewser with, after the NRO path, exactly:

```
envSetNextLoad("sdmc:/switch/brewser.nro",
               "\"sdmc:/switch/brewser.nro\" --fwd=1 --app=<appId>")
```

so Brewser sees `Switch.argv = ["…/brewser.nro", "--fwd=1", "--app=<appId>"]`.

- **`--fwd=1`** — forwarder mode: no catalogue chrome, toolbar forced off, and
  the app-context exit quits to hbmenu at the app root.
- **`--app=<appId>`** — the app to launch; overrides `config.json autorunApp`.
- **Additive-only evolution.** New flags may be introduced later. **Brewser MUST
  forever honour `--fwd`/`--app` and MUST ignore unknown `--`-prefixed flags.**
  A forwarder generated by any Brewser version keeps working on every later
  runtime — this is the load-bearing guarantee.

**Engine dependency:** the leading `--` flags reach JS via `Switch.argv` but must
NOT be treated as an entrypoint override. Engine patch **#120**
(`resolve_entrypoint`, `nxjs-extended/source/main.cc`) skips leading `--` tokens
when selecting the bootstrap entrypoint, so Brewser boots its own
`romfs:/main.js` normally. Hardware-verified 2026-08-13 (probe I2-P). **Citron
does not populate argv**, so forwarders are a real-hardware-only feature.

## 2. `forwarder.json` schema (contract v1)

`romfs:/forwarder.json`, read by the forwarder's own embedded stub (always the
same version that generated it; the `contract` field is a defensive guard):

```json
{
  "contract": 1,
  "appId": "com.example.app",
  "title": "Example App",
  "entry": "index.html",
  "files": [ { "path": "index.html", "size": 12345 } ]
}
```

- `contract` (required) — `1`. Any other value → the stub prints a "made by a
  newer Brewser" error and exits without chainloading.
- `appId` (required) — the id passed as `--app`.
- `title` (optional) — for the stub's console messages.
- `entry`, `files[]` (present **iff** a bundle is embedded):
  - `entry` — the relative entry path, written **last** during seeding and used
    for the installed-test.
  - `files[]` — the embedded bundle inventory. **`size` is the file's byte size
    from `statSync` of the actual installed bytes at generation time (D2)** —
    used only for a post-write size check during seeding. No hashes: the seed
    source is the forwarder's own immutable RomFS, so sizes suffice to catch a
    torn write, and the stub stays dependency-free (no SHA-256).
- **Bundle presence** = `files`/`entry` present AND `romfs:/bundle/` populated.
  Absent ⇒ lite forwarder. Both variants are contract v1.

## 3. Trust model (correction 3a)

The embedded snapshot is **"the installed bytes of the allowlisted paths"** at
generation time — not a signed or pristine copy. Apps may legally overwrite their
own bundle files at runtime (the sandbox permits writes inside `apps/<id>/`), so
the forwarder makes **no pristineness claim**. This is the *identical* trust
surface as a normal Brewser launch of that installed app: whatever bytes are on
disk for the allowlisted paths are what you get. Forwarders are user-generated
and unsigned; they are launchers for a locally-installed/local-snapshot app, not
a distribution channel.

**What the snapshot excludes (deliverable 3):** the snapshot is exactly the app's
install **allowlist** (its artifact inventory), never a directory walk. App-
written runtime data (saves, caches) that lands inside `apps/<id>/` is therefore
never captured, so seeding after a delete can never resurrect stale user data.
All runtime-managed user data (localStorage, IndexedDB, cookies) lives outside
`apps/<id>/` regardless.

**Orphan / removed-file rationale (correction 3b):** a Brewser app *Update*
re-downloads the current artifact set but never deletes files that were removed
between versions, so a walked directory could carry stale old-version files. The
allowlist (the current inventory), not a walk, is what keeps those out of a
snapshot.

## 4. SD paths, naming & collision rule

| Path | Purpose |
|---|---|
| `sdmc:/switch/<sanitizedAppId>-forwarder.nro` | the generated forwarder |
| `sdmc:/switch/<sanitizedAppId>-forwarder.nro.tmp` | in-progress write (revealed by rename) |
| `sdmc:/switch/brewser.nro` | Brewser (chainload target) |
| `sdmc:/switch/brewser/apps/<appId>/` | the app install (seed target) |
| `sdmc:/switch/brewser/configs/app-inventory/<appId>.json` | install allowlist sidecar |

- **Output filename is derived from the sanitized `appId`** (`[^A-Za-z0-9._-]`
  → `_`), never the title (correction 2): two apps with the same display title
  would otherwise overwrite each other's forwarders. hbmenu shows the NACP
  title, so the filename is not user-visible.
- **Regeneration replaces cleanly:** the same app always maps to the same
  filename, so re-creating a forwarder (with either checkbox state) overwrites
  the previous one via `.tmp` → remove-then-rename.

## 5. Generation (inside Brewser, offline)

1. Read `romfs:/forwarder-stub.nro` → decode → reuse its code segment.
2. NACP: title = app name, author = developer, version = app version, id =
   derived title id (§8). UTF-8 limits enforced (§8).
3. Icon: decode the app's cached logo → resample to 256×256 → JPEG. SVG /
   missing / undecodable logo → Brewser's own icon (D6); never blocks.
4. Allowlist (embed only): the install inventory sidecar (§9). If absent and the
   network is reachable, fetch `artifacts/<id>.json` once, persist the sidecar,
   use it (D1). If no authoritative list is available, embed is refused (never a
   directory walk).
5. RomFS: `forwarder.json` (+ `bundle/<rel>` from the allowlist for embed). Bundle
   leaves are lazy SD-file references, so the NRO streams to SD without buffering
   the app bytes.
6. Preflight `openSdmc().freeSpace()` against the computed output size + 32 MiB
   margin (correction 4).
7. Stream to `…-forwarder.nro.tmp` → verify **written size == output size** and a
   re-read `NRO0` magic (correction 1) → remove-then-rename to the final name.
   Any failure removes the `.tmp` so hbmenu never sees a partial file.

---

## 6. Launch flow (the stub)

1. Parse `forwarder.json` (unknown `contract` → error + exit).
2. Verify `sdmc:/switch/brewser.nro` exists (else "install Brewser"
   message; never dies silently).
3. Decide:
   - **installed** (`apps/<id>/manifest.json` + `apps/<id>/<entry>` both exist —
     exactly Brewser's definition) → **chainload now; embedded snapshot ignored**
     (the app always runs at its installed version — never a downgrade).
   - **missing + bundle** → seed the bundle into `apps/<id>/` offline (§7) →
     chainload.
   - **missing + no bundle (lite)** → chainload anyway; Brewser shows a
     missing-app screen.
4. Chainload per §1.

Brewser side (`--fwd=1`): no catalogue, toolbar off, splash independent of
`config.json`. If `--app` names an app that isn't installed (lite forwarder,
deleted app), Brewser shows a graceful missing-app screen (`forwarder-missing`)
— reading the manifest for the entry only after confirming `manifest.json`
exists, so the missing screen never depends on a readable manifest (correction
5). **Exit** walks back within the app, then quits to hbmenu at the app root
(closes the historical autorun no-op-exit gap); `freshProcessOnExit` is ignored
in forwarder mode (a relaunch would boot the plain catalogue).

## 7. Seed staging + FAT-safe swap (D3)

Seeding runs only when the app is **missing**, so there is no good install to
protect. The stub writes the bundle **directly into `apps/<id>/`, entry file
LAST** — mirroring the installer, so an interrupted seed leaves no entry file,
the installed-test fails, and the next launch re-seeds (self-heals). Each written
file's size is checked against `forwarder.json`. On any failure (space, write,
size mismatch) the stub shows "couldn't restore <app>" and exits cleanly to
hbmenu without chainloading into a broken app.

*(Rationale for direct-write over a staging-dir + rename swap: the app is
missing, so nothing needs protecting, and this avoids depending on HOS directory-
rename semantics. If probe I4-P shows direct writes are unsafe, the fallback is
stage → verify → remove-any-partial → rename.)*

**Consequence (D3):** a stub-seeded install is created by the stub, which — to
stay minimal — does **not** write the `configs/app-inventory/<id>.json` sidecar.
So a seeded app counts as "legacy" (no inventory) for any *future* embed
forwarder generated from it, until it is updated/re-downloaded through Brewser
(which writes the sidecar). Link-only forwarders are never affected.

## 8. NACP / icon constraints

- Title < `0x200` UTF-8 bytes per language slot; author < `0x100`; version ≤
  `0x10` bytes (over-limit strings are trimmed byte-safe at generation).
- Icon = 256×256 JPEG.
- **Title id derivation (D5):** deterministic per app —
  `0x0500000000000000 | (FNV-1a-64("brewser-forwarder:" + appId) & 0x0000FFFFFFFFF000)`.
  The high byte `0x05` is outside Nintendo's application-id space (`0x01…`), so a
  forwarder id can never collide with a retail title; it is stable across
  regenerations (a pure function of `appId`). Forwarders are NROs (not registered
  titles), so the id is effectively cosmetic / save-data scoping only.

---

## 9. Install inventory sidecar

`configs/app-inventory/<appId>.json` = `{ id, entry, version, files: [<path>…] }`.
Written by Brewser's installer/updater on a successful install (paths only — sizes
come from `statSync` at generation, D2), removed on uninstall. Stored **outside**
`apps/<id>/` so the snapshot never has to exclude it and the app dir stays == the
bundle. It is the offline-authoritative allowlist for embedding; a missing sidecar
(legacy install, or a stub-seeded install per §7) disables the embed checkbox with
a "re-download to enable" hint (D1). Link-only generation never needs it.

---

## 10. Stub ↔ runtime version-lock

The stub is embedded in `brewser.nro`'s RomFS (`romfs:/forwarder-stub.nro`) and is
version-locked to the runtime by the signed whole-NRO self-update: it rides inside
the NRO whose per-chunk SHA-256 (`dist/update.json`) and atomic swap replace it
wholesale. It is added to `SEED_SKIP_ROOT_FILES` so the seeder never mirrors a
stale copy to the SD card. A *generated* forwarder carries a copy of the stub from
the Brewser version that made it; cross-version compatibility is guaranteed solely
by the argv contract (§1) — old forwarders keep working forever.

---

## 11. Failure behaviours (summary)

| Condition | Behaviour |
|---|---|
| `brewser.nro` absent | Stub: "install Brewser (play.brewser.io)" → exit |
| Unknown `forwarder.json contract` | Stub: "made by a newer Brewser" → exit |
| Seed failure (space/write/size) | Stub: "couldn't restore <app>" → clean exit; live install untouched |
| Lite forwarder, app deleted | Brewser forwarder-missing screen → + exits to hbmenu |
| Generation: SD full / write mismatch | Dialog error; `.tmp` removed; no partial `.nro` |
| Applet-mode launch | Brewser's existing launch-time applet warning (warn-only, D7) |
